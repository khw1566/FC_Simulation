# 울산광역시 80km 전 범위 도로 누락 보완 계획

작성일: 2026-10-11

## 1. 목표와 작업 범위

울산광역시 80km × 80km 맵 전체를 대상으로 도로 원본 수집, 변환, 공간 캐시, 3D 표시, 전술지도까지 누락 경로를 추적하고 보완한다. 일부 장소의 도로를 수작업으로 추가하는 방식이 아니라, 전 범위 처리 여부와 미완료 구역을 기록하는 재실행 가능한 파이프라인을 구축한다.

- 기준 설정: `config/ulsan_metro_80km.json`.
- 경계: 남 35.1841, 북 35.9049, 서 128.81256666666667, 동 129.69843333333336.
- 월드 크기: 80,000m, 중심 위도 35.5445 / 경도 129.2555.
- 대상은 울산 행정경계 내부에 한정하지 않는다. 위 사각형에 포함되는 인접 부산·경남·경북 영역과 경계 교차 도로까지 처리한다.
- 중앙 60km도 다시 조사한다. 외곽 10km 띠만 보완하면 중앙의 생활도로 누락은 남는다.
- 도로가 없는 바다와 미수집 구역은 별도 상태로 구분한다.
- 원본에 없는 길을 임의로 생성하지 않는다. 완료는 채택한 원본과 수집 범위에 대한 완결성을 뜻하며, 현실의 모든 길을 보장한다는 뜻은 아니다.

## 2. 현재 확인한 사실

| 항목 | 로컬 근거 | 의미 |
|---|---|---|
| 80km 런타임 도로 수 | `vector_stream/index.json`의 `counts.roads = 8878`, 9월 30일 건물 병합 결과도 8,878개 | 건물 확장 이후에도 도로 수는 기존 간선 수집 규모로 유지됨 |
| 80km 건물 병합의 도로 출처 | `merge_ulsan_80km_buildings.py`의 `_load_roads()`와 호출부 | 도로는 60km 원본에서 가져와 좌표를 변환함. 외곽 건물 수집이 외곽 도로 수집을 의미하지 않음 |
| 기존 광역 수집 대상 | `tools/integrate_ulsan_metro_roads.py` | 60km 경계와 간선 중심 쿼리 사용. 주거·서비스·보행 도로의 최초 수집 누락 가능 경로가 명확함 |
| 상세 수집기 범위 | `pipeline/collectors/ulsan_detailed_road_collector.py` | `ulsan_metro_60km.json`과 60km 저장 경로가 고정되어 있음 |
| 상세 수집 기록 | `data/raw/ulsan_metro_60km/highways/detailed_cells/manifest_progress.json` | 완료 셀 0개. 2026-09-30 최초 셀 요청의 WinError 10013 기록이 남아 있음 |
| 지도 표시 필터 | `config/simple_vector_maps.json` | 기본 `road_types`가 motorway·trunk·primary·secondary에 제한됨. 3D와 전술지도 누락은 구분해야 함 |
| 전술지도 도로 집계 | 80km `map_meta.json` | 6,614개. 3D의 8,878개와 다르며, 필터·클리핑·생성 시점 차이를 조사해야 함 |
| 외곽 완료 메타데이터 | 80km `map_meta.json`의 `outer_buildings_roads_collected = true` | 건물 병합 코드가 함께 설정하는 값이므로 도로 전 범위 완료의 증거로 사용하면 안 됨 |
| 공간 캐시 사용 | `vector_data_stream.gd` | 원본 크기·수정 시각이 인덱스와 다르면 로딩 오류로 종료함. 도로 JSON만 교체해서는 안 됨 |

위 사실은 현재 로컬 파일과 코드에서 확인했다. 개별 누락 도로의 위치, 전체 도로 유형별 실제 개수, 셀별 공백 분포는 아직 집계하지 않았다. 과거 연결 오류는 기록 확인에 한하며, 현재 네트워크 차단 상태를 재확인한 것은 아니다.

지정 Python312 경로는 현재 존재하지 않으며 `.venv_campus`와 `.venv_optimization`의 실행기는 모두 사라진 기본 Python 경로를 참조해 실행에 실패했다. 구현 첫 단계에서 실행 환경을 정비해야 한다. 이번 계획 작성에서는 맵 실행, API 수집, 원본 에셋 변경을 하지 않았다.

## 3. 누락 원인 분류

| 구분 | 판정 방법 | 대응 |
|---|---|---|
| 수집 범위 누락 | 원본 도로·셀 이력이 60km에 한정되는지 확인 | 80km 전체 격자 수집 |
| 도로 유형 누락 | 원본 유형별 집계와 수집 쿼리 대조 | 생활도로·연결로·보행로·임도 포함 |
| 요청 실패·불완전 응답 | 셀 상태, 응답 오류, 노드 참조 검사 | 실패 셀 재시도 또는 세분화 |
| 변환·병합 누락 | 원본 way ID와 변환 산출물 대응표 대조 | 필터·좌표·클리핑·중복 판정 수정 |
| 캐시 누락 | 런타임 도로와 스트림 배치의 ID·해시·집계 대조 | 동일 리비전으로 캐시 재생성 |
| 3D 표시 누락 | 데이터가 있는 구간의 메시·고도·거리·교량 대체 판정 확인 | 원인이 확인된 표시 조건 보정 |
| 전술지도 누락 | 지도 유형 필터와 SVG·타일 입력 대조 | 축척별 표시 정책 명시 및 수동 재생성 |

수집 범위와 유형 제한은 코드에서 확인한 문제다. 지형 매립, 컬링, 교량 대체, 스트리밍 중복 판정은 조사 항목이며 현재 원인으로 확정하지 않는다.

## 4. 단계별 실행 계획

### 단계 A. 환경 정비와 전 범위 기준선 작성

- 지정 또는 프로젝트 가상환경 Python을 복구하고 필요한 패키지만 확인한다.
- 현재 설정·도로 원본·메타데이터·공간 캐시의 파일 크기, 수정 시각, SHA-256을 기록한다.
- 큰 건물·도로 통합 JSON은 스트리밍으로 읽어 도로 유형별 개수·길이·분포·속성 보유율을 집계한다.
- 월드 좌표를 기준 설정으로 위경도에 대응시키고, 중앙 60km와 외곽을 구분해 분포를 작성한다.
- 원본 way ID가 없는 기존 `rd_metro_*` 항목은 원본 노드열·선형으로 대응시킨다. 순번 ID만으로 동일 도로를 판단하지 않는다.
- 사용자에게서 누락 위치가 제공되면 회귀 사례로 추가하되, 위치 제공 없이도 전체 범위 조사를 진행한다.
- 산출물: `results/ulsan_80km_roads/baseline.json`, `coverage_before.csv`, `coverage_before.svg`.

완료 조건: 전체 경계를 덮는 조사 격자와 현재 도로 분포가 있고, 원본 누락과 표시 누락을 분리할 기준이 마련되어 있음.

### 단계 B. 80km 수집기와 재개 기록 분리

- 기존 수집기를 맵 설정 인자로 동작하도록 분리하거나 80km 전용 진입점을 추가한다. 60km 기존 실행 결과를 덮어쓰지 않는다.
- 전용 원본 경로: `data/raw/ulsan_metro_80km/highways/`.
- 기존 수집기의 0.025도 상한을 그대로 적용하면 기본 격자는 남북 29 × 동서 36 = 1,044셀이다. 경계 전체를 정확하게 분할하며, 과밀 셀을 나누면 최종 셀 수는 증가할 수 있다.
- 셀 ID에는 맵 ID와 격자 규격을 포함한다. 설정·경계·쿼리 해시가 다르면 기존 완료 기록을 재사용하지 않는다.
- 셀 상태: 대기 / 수집 중 / 완료 / 검증된 빈 응답 / 재시도 / 보류. 실패 응답을 빈 셀로 기록하지 않는다.
- 도로 유형: motorway·trunk·primary·secondary·tertiary 및 각 link, unclassified, residential, living_street, service, pedestrian, footway, path, steps, cycleway, track, bridleway, corridor.
- construction·proposed·실내 corridor 등은 원본을 보존하고 현행 지상 도로 표시와 별도 정책으로 분류한다. 알 수 없는 highway 값도 누락 목록에 기록한다.
- 원본 way ID, node ID, version·timestamp가 제공되면 보존하고 bridge, tunnel, layer, width, lanes, surface, access, oneway, junction, foot, bicycle, tracktype 등도 유지한다.
- 첫 소수 셀로 연결과 응답 구조를 확인한 뒤 순차 수집한다. 호출량 제한·대기·지수 백오프를 두고, 시간 초과·과밀 응답은 셀 세분화로 처리한다.
- HTTP 성공만으로 완료 처리하지 않는다. 오류 remark, JSON 구조, 필요한 노드 참조, 파일 해시를 확인한다.
- 네트워크가 차단되면 해당 상태를 보고하고, 같은 형식의 외부 수집 원본 또는 지역 OSM 추출본을 가져오는 경로를 지원한다. 대체 자료의 실제 범위·시점·라이선스는 채택 전에 확인한다.
- 수집기는 원본 저장까지만 수행한다. 기존 수집기의 완료 후 원본 Godot 실행·런타임 자동 덮어쓰기 동작은 새 경로에서 제거한다.

완료 조건: 모든 최종 셀에 확인 가능한 상태가 있고, 미완료 셀을 이어서 수집할 수 있음. 실패·보류가 있으면 전 범위 수집 완료로 표시하지 않음.

### 단계 C. 도로 전용 병합과 좌표 변환

- OSM way ID와 버전 기준으로 셀 중복을 정리한다. 구버전이 신버전을 덮어쓰지 않게 하고 충돌 내역을 남긴다.
- 경계 걸침 way의 전체 노드열을 확보한 뒤 맵 경계와 선분 교차를 계산한다. 경계 내부 노드만 남겨 도로 연결을 끊지 않는다.
- 노드가 빠진 way는 양 끝을 임의로 직선 연결하지 않고 보류·재취득한다.
- 80km bbox → X/Z ±40,000m 변환을 한 모듈로 통일한다. 60km 수치를 두 번 투영하거나 좌표 반전하지 않도록 기준점과 접합 구간을 확인한다.
- 안정된 ID를 `osm_way_<id>`와 클리핑 조각 번호로 구성하고 원본 대응표를 남긴다.
- 위아래로 겹친 고가·터널·평면 도로는 layer·bridge·tunnel을 고려한다. 선형이 같다는 이유만으로 제거하지 않는다.
- 폭은 유효한 width → lanes → 유형별 기본값 순으로 계산하고 출처와 추정 여부를 기록한다. 자전거길은 유형만으로 비포장이라고 확정하지 않고 surface를 우선한다.
- 접근 제한 도로는 원본을 보존하고 가시화와 통행 허용 정책을 구분한다.
- 도로 전용 중간 산출물을 만든 후 기존 건물·터널·방파제 등 다른 필드를 보존하는 병합을 수행한다.
- `merge_ulsan_80km_buildings.py` 재실행이 신규 도로를 60km 도로로 되돌리지 않도록 도로 출처와 보존 계약도 수정한다.
- `coverage`의 건물/도로 완료 상태를 분리하고 도로 범위·유형·수집 시점·미완료 셀을 명시한다.

완료 조건: 유효한 원본 도로마다 산출물 또는 명시적 제외·보류 사유가 있음. 설명되지 않은 변환 누락은 0건.

### 단계 D. 스트리밍·3D·전술지도 반영

- 도로 데이터와 `road_metadata.json`의 ID·점열 해시를 같은 리비전으로 만든다. 기존 순번 기반 보정 메타데이터의 오적용을 막는다.
- `vector_stream_cache.py`를 통해 신규 원본과 일치하는 공간 캐시를 별도 리비전에 생성한다. 캐시 재생성 시 기존 건물 최적화 설정을 유지한다.
- 배치 도로 수, 파일 존재, SHA-256, 원본 크기·수정 시각·해시를 확인한 뒤 활성화한다.
- 기존 1,500m 공간 배치와 근거리 로딩을 우선 유지한다. 전체 도로를 상시 로딩하는 방식으로 해결하지 않는다.
- 긴 도로 배치의 반경, 진입·이탈 거리, 재진입 시 중복 키 해제를 조사한다. 추가 분할이 필요하면 원본 연결 관계를 보존한다.
- `road_segment_classifier.gd`, `road_batch_builder.gd`, `building_road_manager.gd`, 교량 대체 처리에서 삭제·대체·터널 분류 사유를 추적할 수 있게 한다.
- 산악·하천·교량 접근부는 현재 지형·수계 입력을 사용해 지형 매립, 잘못된 수면 분류, 높이 불일치를 조사한다.
- 전술지도는 넓은 축척의 간선 표시와 상세 축척의 생활도로·보행로 표시를 구분한다. 표시 제외 유형·길이를 별도 집계해 데이터 누락과 혼동하지 않게 한다.
- 기존 수동 갱신 정책에 따라 SVG·타일·관련 메타데이터를 재생성한다. 게임 시작 시 수집·생성을 연결하지 않는다.

완료 조건: 데이터·메타데이터·캐시·지도 입력이 같은 도로 리비전을 참조하고 각 단계의 제외 내역을 설명할 수 있음.

### 단계 E. 경량 확인과 최종 교체

- 데이터 확인은 전 범위 자동 집계로 수행한다. 셀 완료율, 유형별 길이, 원본→런타임→캐시 대응률, 경계 교차 연결, 중복·비정상 좌표를 확인한다.
- 육상인데 도로 길이가 0인 셀과 인접 셀에 비해 급격히 적은 셀을 검토 대상으로 뽑는다. 바다·산지 등 실제 무도로 지역은 근거를 기록한다.
- 육교·고가처럼 평면 교차만 하는 길을 연결된 교차로로 오인하지 않는다. 막다른 길과 맵 경계 단절도 오류와 구분한다.
- 시가지 생활도로, 산업단지 진입로, 산악 임도, 하천 횡단부, 중앙/외곽 접합부, 지도 끝의 도로를 독립 소규모 프리뷰에서 확인한다.
- 프리뷰는 `previews/asset_browser/` 전용 경로와 복사본을 사용하고 원본 프로젝트에서 Godot 임포터·에디터를 실행하지 않는다.
- 원본·공유 매니페스트는 교체 직전에 변경 여부를 다시 확인한다. 동시 변경·잠금이 있으면 보류하고 다른 작업의 프로세스를 종료하지 않는다.
- 활성 도로·캐시 리비전을 맞춰 교체하고 이전 정상 리비전으로 되돌릴 수 있게 한다. 다중 파일 교체 도중에는 신규 리비전을 활성화하지 않는다.
- 맵별 매니페스트와 `godot_project/assets/generated/manifest.json`에 해시·bbox·고도 범위·벡터 집계를 기록한다.
- 자산 수정 시 `pipeline/indexer/ASSET_INDEX_GUIDE.md`를 읽고 `.venv_campus/Scripts/python.exe pipeline/indexer/build_asset_index.py`를 실행한다. 해당 가상환경 복구를 선행하며 색인 결과와 보류 파일을 보고한다.
- 전체 맵 실행은 별도 요청 시 수행한다. 독립 프리뷰 결과로 전체 맵 FPS·실행 안정성을 주장하지 않는다.

완료 조건: 전 범위 데이터 확인과 대표 구간 프리뷰를 통과하고, 미완료·제외·원본 한계 및 롤백 위치가 최종 보고에 기록됨.

## 5. 구현 모듈과 산출물 배치안

아래 경로는 구현 시 사용할 제안이며 이번 계획 작성에서 생성한 모듈은 아니다.

| 역할 | 제안 경로 |
|---|---|
| 수집 설정·도로 유형 정책 | `config/ulsan_80km_roads.json` |
| 격자·요청·재개 관리 | `pipeline/collectors/ulsan_roads/` |
| 원본 병합·좌표·클리핑·메타데이터 | `pipeline/processors/ulsan_roads/` |
| 전 범위 누락 집계 | `pipeline/processors/ulsan_roads/coverage_audit.py` |
| 셀 원본·진행 기록 | `data/raw/ulsan_metro_80km/highways/` |
| 도로 전용 중간 리비전 | `data/processed/ulsan_metro_80km/roads/` |
| 집계·전후 비교·보류 목록 | `results/ulsan_80km_roads/` |
| 독립 대표 구간 확인 | `previews/asset_browser/ulsan_80km_roads_check/` |

- 각 모듈은 한 가지 책임을 맡고 주요 클래스는 파일당 하나만 둔다. 600라인에 도달하기 전에 분리하며 800라인을 넘기지 않는다.
- 신규 패키지·모듈은 `__init__.py` 또는 해당 `module_index.json`에 노출한다.
- 새 자산 계열·메타데이터 규약이 생기면 자산 색인 지침과 분류 코드도 함께 갱신한다.

## 6. 우선순위와 완료 판정

- 최우선: Python 실행 환경 복구 → 현재 도로 분포 집계 → 80km 전체 격자와 수집 상태 분리.
- 다음: 80km 간선·연결로와 중앙 생활도로를 먼저 확보하고, 같은 격자 체계로 보행로·임도까지 완료한다. 유형별 중간 진척을 전체 완료로 표기하지 않는다.
- 이후: 원본 병합·경계 연결·좌표 변환 → 건물 병합의 도로 덮어쓰기 방지 → 캐시·메타데이터 반영.
- 마지막: 표시 원인별 보정 → 전술지도 축척 정책 → 독립 프리뷰 → 색인 및 최종 보고.
- 수집 소요 시간은 초기 셀의 응답량·실패율을 측정한 뒤 계산한다. 현재 단계에서 전 범위 완료 시간을 확정하지 않는다.

| 완료 지표 | 기준 |
|---|---|
| 전 범위 수집 | 모든 최종 셀이 완료 또는 검증된 빈 응답. 실패·보류 0셀 |
| 원본 참조 | 채택한 way의 필수 노드 누락 0건 |
| 변환 추적 | 모든 유효 way에 산출물 또는 제외 사유 존재 |
| 경계·연결 | 수집·클리핑 때문에 발생한 설명되지 않은 단절 0건 |
| 캐시 일치 | 원본과 인덱스·배치 도로 수 및 해시 일치 |
| 표시 확인 | 대표 사례의 누락 해소, 의도적 표시 제한은 문서화 |
| 인덱싱 | 자산 색인 갱신 결과와 보류 파일 기록 |
| 상태 보고 | 건물 완료와 도로 완료를 분리하고 원본 등록 한계 명시 |

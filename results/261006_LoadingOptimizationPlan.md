# 울산 80km 맵 로딩 지연 조사 및 최적화 계획

작성일: 2026-10-06. 조사 범위: 현재 로컬 코드, 에셋 파일 크기·구조, 기존 로딩 기록. 실제 맵·Godot 에디터·임포터는 실행하지 않았다. 이번 작업은 조사와 계획 수립이며 실행 코드와 에셋은 변경하지 않았다.

## 1. 결론과 판단 범위

가장 먼저 개선할 대상은 **철도 주변 지형의 재귀 세분화·충돌 생성**, **철도 전 구간의 시작 시 생성**, **넓은 초기 반경의 건물·도로 메시 생성**이다. 대형 파일의 읽기뿐 아니라 읽은 자료를 메인 스레드에서 메시·충돌체로 만드는 작업량이 크다.

- 코드상 확인: 울산 80km는 지형 11×11=121청크를 모두 만든 후 건물·도로 초기화를 시작한다. 그 초기화에서도 공항·교량·문화유산·철도 구성을 마친 뒤 주변 벡터 자료를 처리한다.
- 코드상 확인: 철도 지형 보정기는 원거리 LOD에도 적용되며, 철도와 겹치는 삼각형을 기본 10m 이하 변 길이가 될 때까지 최대 8단계, 단계마다 4개 삼각형으로 재귀 분할한다.
- 코드상 확인: 철도 전 구간의 침목·전차선·노반 메시를 시작 전에 생성한다. 표시 거리 제한은 생성 작업 자체를 생략하지 않는다.
- 통계상 확인: 초기 9.5km 반경과 배치별 반경을 적용하면 건물 63,866동, 도로 2,792개가 후보에 포함된다. 실제 표시 건물 수는 공항 등 대체 영역 필터에 따라 달라진다.
- 판단 한계: 현재 버전의 단계별 실행 시간이 없으므로 특정 파일이 120초 중 몇 초를 차지하는지는 확정할 수 없다. 아래 순위는 실행 경로와 작업량에 근거한 병목 후보 순위다.

## 2. 현재 로딩 경로

`지도 선택 → 이미지 사전 읽기 → main_world 씬 읽기·생성 → 지형 자료 변환 → 121청크 및 초기 LOD 메시·근거리 충돌 → 공항·교량·문화유산 → 울산 철도 전체 및 열차 구성 → 주변 건물·도로 배치 → 조작 허용`

- `godot_project/scripts/services/loading_manager_service.gd`: 시작 시 높이맵·수계 마스크·전술 지도를 사전 읽는다. 월드 씬은 별도 스레드로 읽지만 준비 완료는 지형과 BuildingRoadManager 완료를 기다린다.
- `godot_project/scripts/terrain/terrain_chunk_manager.gd`: 청크 전체 생성 후 `_update_chunks_lod()` 완료까지 기다린다. 개별 메시 계산은 동기식이며 청크 사이에만 프레임을 양보한다.
- `godot_project/scripts/terrain/building_road_manager.gd`: 지형 완료 후 랜드마크와 철도를 순서대로 준비한다. `_load_railways()`를 기다린 다음 벡터 스트리밍을 시작한다.
- `godot_project/scripts/terrain/horizon_terrain_manager.gd`, `industrial_zone_manager.gd`: 지형 완료 뒤 별도 작업을 진행하여 건물·도로 구성과 CPU·메모리·GPU 전송을 경쟁할 수 있다. 로딩 완료 조건에는 이 관리자들이 포함되지 않는다.
- 로딩 제한은 240초다. 제한을 늘리는 것은 최적화가 아니다. 이미지 사전 읽기 대기에는 현재 `_timed_out()` 검사가 없고, 동기식 메시 계산 중에는 UI와 제한 시간 검사도 진행하지 못한다.

## 4. 원인별 우선순위

### P0: 철도 주변 지형 세분화와 충돌

관련 파일: `terrain_chunk_manager.gd`, `terrain_chunk.gd`, `railway_terrain_grader.gd`, `railway_terrain_void.gd`.

- 철도 보정기를 121청크 모두에 전달한다. 기본 LOD 해상도는 128/64/32다.
- 청크 폭은 약 7,273m다. 원거리 32격자의 기본 셀 폭도 약 227m지만 철도 주변은 10m 기준으로 재귀 분할한다. 원거리 지형의 단순화 이점을 상당 부분 상쇄할 수 있다.
- `SurfaceTool` 정점 추가·법선 생성·commit을 한 번에 수행한다. 프레임 양보가 청크 내부 계산을 나누지는 않는다.
- LOD0 충돌은 `railway_terrain_void.collision_shape()`에서 메시의 각 삼각형에 대해 마스크 범위를 검사하고 오목 다각형 충돌체를 생성한다.
- 개선: 경량에서는 근거리만 철도 세분화하고 중·원거리는 사전 보정 높이맵과 노반 외형을 사용한다. 정밀 충돌은 실제 이동 주변의 제한 반경에서 생성한다. 터널 입구와 진입 구역은 예외로 정확한 지형·충돌을 보장한다.
- 개선: 철도 마스크의 비어 있는 공간을 청크·셀 인덱스로 먼저 제외한다. 정적 메시와 충돌은 가능한 부분을 파이프라인에서 미리 생성한다.

### P0: 철도 전체 생성이 시작 완료를 가로막음

관련 파일: `building_road_manager.gd`, `railway_world_manager.gd`, `railway_track_builder.gd`, `railway_formation_builder.gd`, `railway_train_service.gd`.

- 정렬된 선로 좌표의 3차원 길이 합계는 약 437.10km다. 여러 선로의 합계이며 중복 없는 노선 길이를 의미하지 않는다.
- 777개 구간 전체를 약 500m 청크로 나누고 모든 청크의 도상·레일·전차선·침목·전주·노반을 만든다. 침목 간격은 0.75m 또는 1.2m여서 전체 구성량은 수십만 인스턴스 규모가 될 수 있다.
- 8청크마다 프레임을 양보하지만 총 생성량은 동일하다. `visibility_range_end`만 줄여도 생성 시간이 줄지는 않는다.
- 개선: 노선·시간표 등 논리 정보와 표시 메시를 분리한다. 초기에는 시작 지점 주변의 간략 선로만 준비하고 상세 침목·전주·야간 조명·열차 모델은 거리와 품질에 따라 생성한다.
- 개선: 교량·역사 모델도 거리별 큐로 전환한다. 건물 대체 영역 정보는 모델 생성 전에 제공하여 지연 로딩 시 원본 건물과 겹치지 않도록 한다.

### P1: 초기 벡터 반경과 메인 스레드 메시 생성

관련 파일: `vector_data_stream.gd`, `building_road_manager.gd`, `building_mesh_builder.gd`, `road_mesh_builder.gd`, `road_terrain_tessellator.gd`.

- 울산 80km의 표시 거리는 8km이고 초기·후속 요청 반경은 9.5km다. 여기에 배치 반경을 더하여 후보를 선정한다.
- 시작 후보가 1,476배치다. 건물은 생성한 뒤 소형 건물 컬링을 적용하므로 표시 생략이 초기 생성 비용을 없애지 않는다.
- 배치 파일 읽기·SHA-256·JSON 파싱은 메인 스레드에서 수행한다. 건물 배치 메시 생성에도 내부 프레임 예산 분할이 없다.
- 도로는 지형 격자·대각선에 맞춘 폴리곤 절삭과 교량·터널 구성 비용이 있다. 한 도로 내부 작업은 프레임 예산을 초과할 수 있다.
- 후속 갱신은 0.1초 간격으로 전체 배치 인덱스를 순회하며, 로드된 도로는 이탈 시 해제하지 않아 이동에 따라 상주량이 누적된다.
- 개선: 최초 조작 허용 반경을 표시 반경과 분리하고 2km부터 시작한다. 소형 건물·골목은 생성 전 필터링하고 먼 구역은 간략 표현을 사용한다. 건물·도로 읽기와 배열 계산을 작업 큐로 분리하며 공간 셀 조회와 도로 해제를 추가한다.

### P1: 높이맵 이중 읽기와 대형 이미지 복제·전송

관련 파일: `loading_manager_service.gd`, `map_image_preloader.gd`, `terrain_chunk_manager.gd`.

- 실제 사용할 보정 높이맵 경로를 사전 로더가 알지 못하여 원래 높이맵을 먼저 읽고 철도 높이맵을 다시 읽는다.
- RF 높이맵 한 장은 약 121MiB다. 원본 이미지·복제·청크 분할 이미지·GPU 텍스처가 별도로 생겨 압축 PNG 크기보다 훨씬 많은 메모리를 소비한다.
- `coast_height_texture`와 `create_road_material()`의 높이 텍스처도 각각 생성된다. 렌더용 마스크는 복제 후 밉맵을 만든다.
- 개선: 품질·지도에 따른 최종 경로를 먼저 확정하고 그 파일만 읽는다. 공통 높이 텍스처를 재사용하고 로딩 캐시의 불필요한 원본을 적시에 해제한다. 경량 높이맵과 마스크는 사전 생성하여 읽기·변환·전송 자체를 줄인다.
- 보정 높이맵 생성 시 해안·철도·공항 보정 이력과 원본 해시를 기록한다. 이미 적용된 보정을 런타임에서 반복하지 않도록 한다.

### P2: 배경 지형·공단·지도와 부가 모델

- 배경 지형은 이미 스레드 계산을 사용하지만 약 26.54MiB JSON과 64MiB 고도 배열을 읽고, 설치 단계에서 대형 PNG를 동기식으로 읽는다. 조작 가능 이후의 별도 큐로 미루고 경량 광역 표본을 제공한다.
- 공단은 이미 프록시와 거리별 상세 모델 구조를 사용한다. 다만 상세 모델 첫 사용 시 `industrial_asset_factory.gd`가 GLB를 파싱하고 모든 메시의 trimesh 충돌을 만든다. 프레임당 2개라는 개수 제한만으로는 단일 모델의 긴 처리를 막지 못한다.
- 공단 비활성 설정도 현재 `configure()`의 도로·프록시 생성 이후 적용된다. 설정을 초기화 전에 확인하여 불필요한 작업을 피한다.
- 지도 SVG와 타일 래스터화는 보조 후보다. 전체 지도는 필요 시 읽고 미니맵에는 작은 사전 렌더 이미지, 확대 지도에는 기존 타일 방식과 캐시 공유를 적용한다.
- F9 에셋 도구는 시작 때 UI를 만들지만 목록 `_reload()`는 열기 동작에서 실행한다. 13.99MiB `asset_index.json`을 맵 시작 지연의 직접 원인으로 볼 근거는 없다.
- 그림자·MSAA·구름은 첫 표시 후 성능과 GPU 준비에 영향을 줄 수 있지만 CPU 생성 지연의 최우선 개선 대상으로 삼지 않는다.

- 지형·벡터·철도·공단이 같은 품질 설정을 참조하게 한다. 지도 모델의 지리 정보와 사용자 품질 정책은 별도 책임으로 둔다.

## 6. 구현 순서와 파일 분리

### 1차: 측정과 낮은 비용의 경량 기본값

- 단계별 시간·처리량 기록을 추가한다. 이미지 읽기, 높이맵 변환, 청크별 기본/세분화 메시, 충돌, 랜드마크, 철도, 벡터 읽기·해시·파싱·생성·전송을 구분한다.
- 기록에 지도 ID, 품질, 자산 해시/수정 시각, 캐시 상태, PC·렌더러 정보, 첫 조작 시간, 최장 메인 스레드 작업, CPU/GPU 메모리를 포함한다.
- 철도 보정 높이맵을 사전 로딩 경로에 포함하고 중복 높이 텍스처를 제거한다.
- 지도 선택 UI·설정 저장·품질 정책을 추가한다. 최초 반경을 줄이고 먼 소형 건물은 생성 전에 제외한다.
- 철도 주변 재귀 세분화를 근거리로 제한하고 정밀 충돌을 표시 LOD와 분리한다. 터널 관련 처리를 생략하여 잘못된 충돌을 만드는 방식은 피한다.

### 2차: 시작 완료 조건과 철도 스트리밍

- `최초 안전한 조작 가능`과 `추가 구역 준비`를 구분한다. 지형·필수 충돌·주변 간략 건물·주요 도로만 초기 완료 조건으로 삼는다.
- 철도 표시 청크에 공간 인덱스·간략/상세 단계·해제 반경을 추가한다. 전 구간 논리 노선 계산과 메시 생성을 분리한다.
- 랜드마크·배경 지형·공단·지도 확대용 자료를 우선순위 큐에 배치한다. 상세 자산이 준비되지 않아도 간략 대체 표현은 유지한다.
- 단일 큰 작업을 나누고 계산 배열을 스레드에서 준비한다. 씬 트리 변경과 GPU 제출은 메인 스레드의 제한된 큐에서 수행한다.
- 로딩 취소 시 세대 식별자로 오래된 작업 결과를 버린다. 실패·취소·일시 잠금 시 마지막 정상 캐시를 유지한다.

### 3차: 파생 자산과 상주량 관리

- `pipeline/processors`에 품질별 높이맵·마스크·정적 철도 메시 생성기를 추가한다. 정상 산출물이 완성된 뒤 참조를 전환하고 변경·잠금 파일은 보류한다.
- 건물·도로 공간 인덱스와 간략 표현을 생성하고 도로 이탈 해제·히스테리시스를 적용한다. 배치 수 감소는 중복 읽기를 늘리지 않도록 셀 단위 패키지와 함께 검토한다.
- 공단 모델의 충돌을 근거리에서만 준비하며 단순 충돌 또는 사전 생성 충돌 자산을 사용한다.
- 해시 검증은 유지한다. 준비된 자산의 무결성 확인을 비동기화하거나 동일 세션 캐시를 활용하며 단순 삭제로 속도를 얻지 않는다.

예정 모듈 배치:

- `scripts/models/render_quality_profile.gd`: 품질 값과 유효성 검사.
- `scripts/services/render_quality_service.gd`: 선택·저장·현재 세션 품질 정책 전달.
- `scripts/services/world_startup_coordinator.gd`: 필수 준비·추가 작업·취소 상태.
- `scripts/terrain/terrain_collision_scheduler.gd`: 이동 주변 충돌 요청·해제.
- `scripts/terrain/railway_chunk_stream.gd`: 철도 거리별 표시 작업.
- `scripts/services/startup_timing_recorder.gd`: 단계별 측정 기록.
- `pipeline/processors/build_quality_variants.py`: 파생 자산 생성 진입점. 높이맵·마스크·철도 처리는 하위 모듈로 분리.

현재 `building_road_manager.gd`는 580줄이므로 새 책임을 직접 덧붙이지 않는다. 600줄 도달 전 초기화 조정과 랜드마크 로딩을 별도 모듈로 분리한다. 새 모듈은 `module_index.json` 또는 해당 패키지 인덱스에 등록하고 파일당 단일 주요 엔티티를 유지한다.

특히 지형 해상도를 변경할 때 `terrain_chunk.gd`만 수정해서는 안 된다. `building_road_manager.gd:400`의 도로 절삭 간격과 `shaders/road_surface.gdshader:32`의 보간 해상도도 현재 128 기반이다. 품질별 실제 격자 값을 공유해야 도로가 뜨거나 지형을 관통하는 회귀를 막을 수 있다.

## 7. 최소 검증과 목표

이번 조사에서는 새 로딩 테스트를 실행하지 않았다. 아래는 구현 후 확인 계획이며 성능 보장이 아니다.

- 기존 `results/map_loading_validation.json`에는 23.327초, 최장 프레임 1298ms, 정적 메모리 약 725.91MiB가 기록되어 있다. 별도 로그에는 28.828초도 있다.
- 해당 기록은 10월 3일이고 철도 보정 높이맵·관련 지형 코드는 10월 4일 변경되어 있다. 기존 결과를 현재 버전의 기준선으로 사용하지 않는다.
- 먼저 별도 경량 하네스에서 청크 1개, 철도 청크 1개, 벡터 배치 일부만 확인한다. 원본 프로젝트 임포터나 전체 맵 실행은 이번 작업에 포함하지 않는다.
- 확인 항목은 도로·지형 경계 일치, 해안·공항 평탄화, 터널 진입과 충돌, 이동 중 선행 로딩, 취소 후 복귀, 품질 저장·재시작, 다른 지도에서도 과도한 자산 생성이 없는지다.
- 실제 80km 맵의 cold/warm 비교는 사용자가 전체 로딩 실행을 요청한 경우에 수행한다. 동일 장비·버전·자산을 고정하고 최소 3회씩 첫 조작 시간과 최대 지연을 비교한다.
- 경량 품질의 초기 목표: 첫 조작 15초 이내, 장시간 정지 작업 100ms 이하, 이동 중 추가 작업 예산 약 2ms/프레임. 기준선 확보 후 목표의 현실성을 조정한다.
- 경량의 초기 생성·상주 건물 수와 철도 상세 인스턴스 수가 실제로 감소해야 한다. 화면에서 숨기기만 하고 생성량이 같은 변경은 완료로 보지 않는다.
- 전체 준비 완료 시간과 첫 조작 시간을 별도로 기록하여 단순히 작업을 뒤로 미룬 효과와 실제 비용 감소를 구분한다.

## 8. 인덱싱 및 동시 작업 보호

- 이번 변경은 이 보고서 추가뿐이다. 에셋·코드 모듈을 추가·수정·삭제하지 않아 자산 인덱스 재생성은 수행하지 않았다. 이번 조사에 따른 보류 에셋 작업은 없다.
- 향후 파생 자산 구현 시 `pipeline/indexer/ASSET_INDEX_GUIDE.md`를 읽고 `.venv_campus/Scripts/python.exe pipeline/indexer/build_asset_index.py`를 수동 실행한다. 결과와 보류 파일을 구현 보고에 기록한다.
- 새 품질 자산 분류·메타데이터 규약은 지침과 분류 코드에 함께 추가한다. 생성 매니페스트에는 해시, bbox, 고도 범위, 해상도, 품질, 보정 이력 및 원본 참조를 기록한다.
- 게임 시작에 인덱스 생성기를 연결하지 않는다. 원본 자산 삭제, 실행 중 게임·다른 프로세스 종료, 프리뷰 캐시의 임의 변경은 하지 않는다.

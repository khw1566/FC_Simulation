# 울산 좁은 도로·산책로·산악 임도 복원 작업 보고서

## 원인

- 현재 울산 60km 원본 도로 8,878개는 `motorway`부터 `tertiary` 계열에만 분포한다.
- `residential`, `service`, `footway`, `path`, `steps`, `track`, `bridleway`, `cycleway`, `pedestrian`, `living_street`는 원본 수집 자료에 없다.
- 기존 광역 도로 수집 쿼리가 `motorway|trunk|primary|secondary|tertiary`로 제한되어 있어 생활도로·보행로·산악 임도가 애초에 취득되지 않았다.

## 복원 구현

- Overpass 셀 수집기를 추가했다. 울산 60km 경계를 약 0.025도 격자로 나눠 총 594셀을 대상으로 하고, 한 번 실행할 때 최대 120셀을 수집한다.
- 수집 대상에 주거·서비스 도로, 보행자 도로, 보도, 산책로, 계단, 자전거길, 임도, 승마로를 포함했다.
- 셀별 응답 캐시, 완료·실패 매니페스트, OSM 노드/way 식별자 중복 제거, 실패 지점 재개를 지원한다. 모든 셀이 끝나면 기존 런타임 도로 통합과 도로 속성 매니페스트 갱신을 자동 수행하도록 연결했다.
- 도로 폭은 OSM `width`와 `lanes`를 우선하고, 없으면 도로 분류와 임도 등급(`tracktype`)에 따른 유형별 폭을 적용한다. 표준 OSM 폭 정보가 없는 길의 수치는 시각화 추정값이다.
- 보행로·산책로·계단·승마로는 별도 저상 지형 밀착 재질로, 임도·자전거길은 비포장 재질로 분리했다. 산길의 좁은 폭과 저상 여유를 적용하며 기존 고속도로·간선도로 처리는 유지했다.
- 신규 수집기와 렌더러 및 셰이더 항목을 모듈 색인에 반영했다.

## 실행 상태와 제한

- 신규 수집기를 실제 실행했지만 외부 Overpass HTTPS 연결이 Windows 오류 10013으로 차단됐다. 후보 첫 셀 `ulsan_roads_y00_x00`의 두 엔드포인트 요청은 실패했다.
- 완료 셀 0/594이며, 기존 8,878개 런타임 도로 자산에는 신규 산책로·임도 피처가 추가되지 않았다. 시각화 코드는 준비됐지만 데이터가 도착해야 게임 내 새 길이 나타난다.
- 진행 기록은 `data/raw/ulsan_metro_60km/highways/detailed_cells/manifest_progress.json`에 저장했다.
- 네트워크 접근이 가능한 환경에서 `python pipeline/collectors/ulsan_detailed_road_collector.py`를 반복 실행하면 완료 셀을 건너뛰고 이어서 수집한다. 수집된 모든 셀을 완료하면 런타임 도로 재생성과 속성 인덱싱이 자동으로 실행된다.
- 실행 환경에서 Godot 시각 검증은 수행하지 않았다. OpenStreetMap의 산길·보행로 등록 누락은 별도 현장 자료가 없는 한 완전 복원할 수 없으며, 폭 태그가 없는 길의 폭은 추정치다.
